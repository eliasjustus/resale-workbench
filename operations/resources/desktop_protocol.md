# Proposed business-desktop inspection protocol

This is a configurable evidence checklist, not permission to buy, inspect private
data, repair equipment or run commands. Actual tool availability, competence,
ownership/access and management/activation release need reviewed evidence.

Bind the exact CPU, RAM configuration, storage devices, hardware revision and
included accessories to the target variant. Record observed values separately
from expected values. Unknown configuration stays unknown. A different variant
requires its own assessment and comparable evidence.

An enabled local protocol must cover every required check below and specify its
method, retained evidence, pass rule and abstention rule. Document the actual
display, input device, compatible power connection, firmware inventory method
and storage-health diagnostic capability. Their presence in this checklist does
not establish their availability, safety, authorization or the inspector's skill.

| Check | Required evidence scope |
| --- | --- |
| configuration | Exact CPU/RAM/storage/revision; firmware observations without private data access |
| power_on | Observed start and stable basic operation; never sufficient alone |
| memory | Reviewed nondestructive coverage appropriate to the exact installed configuration |
| storage_health | Reviewed device health observations and limitations; no user-file inspection |
| display | Actual output/interface coverage required by the target offer |
| ports_network | Claimed ports and network functions, with unavailable coverage explicit |
| thermal_stability | Reviewed bounded observation method and its limits; no improvised stress test |
| management_activation | Reviewed management-lock and activation-release evidence |
| accessories | Exact included accessories and relevant compatibility/function evidence |

Keep failed checks and unavailable tests visible. A seller's diagnosis or a
forecast of repair success is not an observed function test. A power-on photo
cannot establish the rest of the protocol. `current_condition`, `if_repaired`
and `parts_out` are separate assessments; do not replace current evidence with
post-repair sales or rewrite an old repair-schema-1 object.

The initial engine evaluates evidence only. Repair, sanitization, user-data
access, destructive tests, battery/mains-power repair and safety-critical repair
are unavailable actions. Any later intervention requires a separately reviewed
scope, actual authority and qualified capability. This checklist executes none.
